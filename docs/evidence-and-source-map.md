# 분석 근거와 빌드 소스 대응표

이 문서는 분석 문서의 관찰 결과와 실제 빌드에 사용되는 확정 소스를 구분하여 기록합니다.

## 1. 확정 절차

```text
완료본·원본 바이너리·역어셈 관찰
        ↓ 수동 대조와 주소/섹터 계산
원본 바이트·결과 바이트·문자·토큰을 포함한 확정 행
        ↓ 원본 바이트 가드
Python 직접 바이너리 기록
        ↓ 재파싱·해시·테스트
재현 결과
```

완료본은 분석 결과와 빌드 결과를 대조합니다.

## 2. 영역별 확인 항목

### 원본 D88

- D88 헤더와 트랙 디렉터리
- 실제 섹터 오프셋과 payload 길이
- 원본 전체 크기와 SHA-256
- 각 raw 변경 행이 가리키는 섹터·파일 오프셋

빌더는 먼저 원본 구조를 확인하고, 확정 행의 원본 바이트가 실제 입력과 일치할 때만 결과 바이트를 기록합니다.

### 이벤트 블록 1~6

각 블록은 원문과 한글 번역을 별도로 보존하며, 제어 토큰과 일반 문자 바이트를 섞어 문자열로 추정하지 않습니다. `block-*-raw-changes.csv`는 문자·제어 단위로 한 행을 사용하며, 바이트별 주소와 이전·이후 값을 공백으로 구분한 배열에 같은 순서로 기록합니다. JSONL 자료는 원문·번역·검증 맥락을 제공합니다.

### 게임오버

고정 세그먼트 15개와 스크롤 블록 35개를 분리합니다. 스크롤 데이터의 제어 토큰, 종결자, 보류 영역은 일반 텍스트로 합치지 않습니다. `source/tables/gameover/hold-34-35.json`은 한 바이트 보류 패치를 기록합니다. `tools/valis_rebuild/serializer.py`의 `apply_hold_patch`는 CHRN 섹터, 원본 바이트, RAM 기준 주소와 D88 역배치 주소의 대응을 검사하며, raw `5C→4A`를 디코딩한 값이 `42→30`과 일치하는지도 확인합니다.

### 엔딩

엔딩은 24개 세그먼트의 순서·길이·종결자·물리 위치를 각각 기록합니다. 길이가 달라지는 경우 주소나 남은 공간을 추측하지 않고, 확정된 raw 변경표의 위치와 바이트를 사용합니다.

### 로고와 ERROR 07

로고 편집 입력은 `source/GFX/`의 여섯 PNG입니다. `source/tables/logo/source-map.csv`가 각 PNG의 그룹, plane, RAM 시작 주소, source 길이, 크기, 인코더와 기준 픽셀 해시를 선언하며 빌더가 이 값을 그대로 읽습니다. 기본 이미지에서는 `source/tables/logo/raw-changes.csv`의 검토된 최종 raw 바이트를 사용해 릴리스 출력을 그대로 재현하고, 픽셀이 바뀐 그룹은 PNG를 같은 길이의 게임 source stream으로 재인코딩한 뒤 `ram-to-raw-map.csv`와 원본 바이트 가드로 적용합니다. 인코더 call-map 파일은 분석 근거이며 실행 설정이 아닙니다. ERROR 07은 명령 스트림 관찰과 최종 raw 변경표를 별도로 보존합니다.

### KANJI1

`assignments.csv`는 글리프의 Unicode 코드포인트, 슬롯, 토큰, ROM 오프셋을 기록합니다. 각 글리프 파일은 16×16 행 데이터를 보존하며, 빌더는 이 명시적 행을 사용해 ROM을 생성합니다.

## 3. 제어 토큰 원칙

제어 토큰은 일반 문자처럼 번역하지 않습니다. `control-token-registry.json`과 각 컴포넌트의 토큰 행을 기준으로 다음을 확인합니다.

- 토큰의 바이트 길이
- 토큰의 의미와 적용 위치
- 토큰 뒤에 오는 문자 또는 데이터의 경계
- 종결자와 패딩의 구분
- 원본·결과에서 보존되어야 하는 제어 바이트

주소와 바이트는 근거 표에 기록된 값을 사용합니다.

## 4. 주소와 섹터 계산의 역할

분석 단계에서 RAM 주소, 파일 오프셋, 트랙·섹터 위치는 서로 다른 주소 층으로 기록합니다. 빌드 단계에서는 이미 확정된 파일 위치와 원본 바이트를 사용합니다. 계산은 다음을 검증하기 위한 것이지, 확정되지 않은 위치를 추정하기 위한 것이 아닙니다.

- raw 행이 올바른 섹터에 속하는가
- payload 범위를 벗어나지 않는가
- 변경 길이가 해당 행과 일치하는가
- D88 재직렬화 후 트랙·섹터 구조가 유지되는가

## 5. 완료 판정

다음 조건을 모두 만족해야 합니다.

1. 원본 D88/ROM 해시와 크기가 입력 계약과 일치한다.
2. 확정 소스의 모든 경로와 행이 유효하다.
3. raw 변경표의 원본 바이트 가드, 게임오버의 주소·토큰 길이 검사와 컴포넌트 간 중복 검사에 통과한다.
4. D88과 KANJI1 출력이 다시 파싱된다.
5. 통합 테스트가 통과한다.
6. 같은 입력으로 반복 빌드한 결과의 해시가 같다.
7. 기본 소스로 만든 결과가 기준 해시 및 완료본과 일치하며, 편집한 소스는 재빌드한 결과와 일치한다.
